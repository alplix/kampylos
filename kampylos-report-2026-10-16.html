Kampylos: a 1.5–2× faster CPU app with identical results, and what the shipped binaries are missing

Against alplix/kampylos master 12cb505 (submodule alplix/VBMicrolensing@a56b7bf), 2026-10-16. All measurements were taken on a bitboinc volunteer host: Apple M1, macOS 15.7.4, BOINC client 8.2.10, Apple clang 14. Follow-up to the reviews of 2026-10-10 and 2026-10-12.

1. Summary

  1. The CPU app can be about 2× faster with a byte-identical result file, without touching the search code. Build VBMicrolensing without the thread_local patch (the CPU app is single-threaded and does not need it) and link a faster allocator. One synthetic work unit: 1066 s with the build lines in boinc/README.md, 536 s with both changes (1.99×); the kampylos_v12_macos_arm64 binary the server ships takes 839 s on the same input (1.57×; newer compiler, same two overheads). Branch build/faster-cpu-app on rilian/kampylos adds a --strip mode to vendor/patch_vbm_thread_local.py and documents the build. Details and evidence in §2.
  2. The macOS binaries the server ships do not contain the fixes merged on 2026-10-11. kampylos_v12_macos_arm64 still restarts from cell 0 when the checkpoint and the output disagree, and kampylos_metal_v2_macos_arm64 has no in-cell checkpoint, leaves fast math on and never checks a command buffer. Rebuilding both from 12cb505 and releasing them as new versions is all that is needed. §3.
  3. Two open items: a Metal task that gets no device from MTLCreateSystemDefaultDevice() still fails the work unit (branch fix/metal-device-unavailable), and the rsc_fpops_est of some work units is 20–50× too low (an event whose tasks take 4–8 CPU-days each is estimated at 4 hours). §4.

2. CPU app: the same answer in half the time

2.1 Where the time goes

Both overheads are in VBMicrolensing, not in Kampylos (Nelder-Mead, the flux fit and the seeding together are under 0.2 % of the samples):

  • Thread-local storage. The fork turns the library's 242 function-local static declarations (577 variables) into thread_local so that the GPU apps' four completion threads can share it. Apart from that keyword and the VBM_THREAD_SAFE define, the fork is byte-for-byte upstream v5.6 (diff of e7c7404 against a56b7bf, ignoring line endings). On macOS every access to a thread_local is a call into libdyld; the CPU app is single-threaded and gets nothing for it.
  • Allocation. Every magnification creates and deletes many small objects (_theta, _point, _curve, _skiplist_curve, image lists), and the finite-source contour integration creates far more. The macOS system allocator spends about a third of the run in tiny_malloc / free_tiny.

2.3 How to apply it (branch build/faster-cpu-app)

  1. CPU app only: strip the thread_local patch before building. The branch adds the reverse of the existing patch script: 
    python3 vendor/patch_vbm_thread_local.py --strip      # fork -> plain upstream v5.6, VBM_THREAD_SAFE removed
# ... build the CPU app as in boinc/README.md ...
git -C vendor/VBMicrolensing checkout -- .           # restore the fork before building a GPU app
    --strip refuses to run unless it finds exactly the 242 + 1 thread_local statics of v5.6, and it removes the VBM_THREAD_SAFE marker, so a GPU app built from a stripped checkout by mistake runs its completion step on one thread (kampylos_cpu_patch_pool.h already checks the marker) instead of corrupting the heap. The GPU apps keep the fork as it is.
  2. All apps: link a faster allocator. Measured with jemalloc (libjemalloc.a on the link line, no source change). mimalloc is the portable equivalent (Linux, Windows, macOS): #include <mimalloc-new-delete.h> in one translation unit and link its library. VBMicrolensing allocates with new, so overriding new/delete covers the hot path. The GPU apps' four completion threads benefit too (the thread_local + jemalloc row: 1.25–1.33× on the host side).
  3. Check every new build the way this report did: build fit_event the old way and the new way, run the same work unit through both and cmp the result files. On one toolchain they must be byte-identical. tests/test_cpu_resume passes with the stripped library (35 s instead of 66 s).

Other platforms (not measured). On Linux a thread_local in the executable is a thread-pointer-relative load, so there the gain should come mostly from the allocator. Where TLS is emulated (MinGW-w64 GCC; Android NDK below API 29) the patch costs more than on macOS: 1.2–1.3× slower than the documented macOS build in the table above, 1.7× slower than plain statics. If the Windows or Android CPU apps are built that way, they gain the most.

2.4 What was tried in the algorithm itself: nothing material that keeps the result

The order matters because VBMicrolensing's root solver starts from the previous call's roots (zr in NewImages, a function-local static), so a magnification can differ in its last bit depending on which point came before it. Two consequences worth knowing: (a) the seed order does not matter: seeds 0, 1, 2, 3, 100, 200 of the ev25055 cell run forwards and backwards gave bit-identical per-seed fits (only the cell's final re-evaluation moved, in the 13th digit), which is what the seed-split part i K work units and the seed-level resume rely on; (b) a resumed process can differ from an uninterrupted one at that level, which is why the Metal end-to-end resume test accepts rounding-level differences.

Faster but not the same result, so not proposed (from the 2026-10-07 review): the far-field single-lens shortcut (up to ~3× per evaluation, changes A at the 1e-5 level), dropping the mirror-image half of the seeds, looser tolerances or fewer iterations.

3. The shipped macOS binaries are older than master

GitHub has not changed since 2026-10-11 17:05 UTC (master 12cb505, submodule a56b7bf; no new pushes, PRs or issues). The binaries this host received are built from earlier code (strings on projects/bitboinc.athena.org.tr/*):

binary (server version, received)what it containswhat master has that it lacks
kampylos_v12_macos_arm64 (CPU 12, 2026-10-12)prints "v4"; seed-level checkpoint and resume ("resuming cell %d at seed %lu"); the old resume path: "checkpoint says %d cells done but the output file doesn't match -- restarting from cell 0"cell checkpoint after every cell, written atomically; resume from the complete lines of out (none of the messages added on 2026-10-11 is in the binary: "output file holds %d complete cells", "could not write the cell checkpoint", "could not trim the output file", "this backend cannot run a seed-split work unit")
kampylos_metal_v2_macos_arm64 (Metal 2, 2026-10-04)prints "v1"; cell checkpoint only; "no Metal device found" → boinc_finish(1)in-cell checkpoint (the batched driver's state); fast math switched off and verified by the self-test kernel (the binary has no setFastMathEnabled: / setMathMode: call, and with fast math on the double-single arithmetic degrades to float32: the comment in kampylos_metal_fit.mm records the synthetic planet cell converging to chi2 692 instead of 411); command-buffer status checks and retries
Rebuild both from 12cb505 and release them as new app versions, with -DKAMPYLOS_VERSION='"13"' and -DKAMPYLOS_METAL_VERSION=... so the version printed in stderr matches the server's. Only the two macOS arm64 binaries were inspected; the other platforms' binaries may be in the same state. The seed-level checkpoint in the shipped CPU app does work: the two ev25055 tasks running on this host have seed checkpoints at seed 63 and seed 43 of 240 after 25 and 36 CPU-hours.

4. Open items

4.1 Metal: a task without a device still fails the work unit

src/kampylos_metal_fit.mm:545 calls only MTLCreateSystemDefaultDevice(); boinc/main_kampylos_metal_boinc.cpp then ends the task with boinc_finish(1). A task started by the BOINC daemon without a window-server session can get nil there (Apple documents that the call resolves the display's GPU and needs CoreGraphics linked), and it is then reported as a computation error. Branch fix/metal-device-unavailable (applies cleanly to master) falls back to MTLCopyAllDevices(), turns "no device", a failed self-test and a persistently failing command buffer into boinc_temporary_exit(300) so the task keeps its checkpoints and is retried, and links CoreGraphics. Exercised with forced-nil builds on 2026-10-12.

4.2 Work-unit cost estimates

The three ev25055 tasks this host received on 2026-10-14 (deadline 2026-10-28) are on course for about 96 and 199 CPU-hours each (24 and 50 minutes per seed, 240 seeds), while the 152 Kampylos tasks the host finished on 2026-10-12…14 took a median of 6 minutes. The server sends rsc_fpops_est = 9e13 for them, which at this host's benchmark (5.86 GFLOPS) is 4.3 hours, 22–46× too low, so the client fetches more of them than it can finish by the deadline. The anchor line shows why they are expensive: FSPL with u0 = 1.2e-12, tE = 1207 d, rho = 1e-5, fb = 529 against fs = 0.32, n_peak = 1191 of 1191 points, chi2dof_base = 0. No point is on the baseline, every binary seed starts with the source inside the Einstein ring for the whole light curve, and 99 % of the time is VBMicrolensing's finite-source contour integration. Two server-side options: scale rsc_fpops_est with the expected cost (for instance from the anchor's n_peak/npts, which the single-lens stage computes in a second), or screen events whose single-lens fit has no baseline before generating their grid.

5. Verification and limits

  • Per-seed fits: identical %.17g output across every build variant on both workloads (§2.2).
  • Whole work units through fit_event: the documented build and the proposed build write byte-identical out files for the synthetic planet (§2.2) and for a cell of the bundled OGLE light curve (tests/sample_ogle_blg1900.dat, magnitudes, 448 points, mag 0.3 0.3 1 -2.5 -2.5 1 log10: chi2 2811.6732 from both builds, 581 s against 301 s with two other processes running).
  • The README recipe as written (--strip, build, restore) was run from the repository checkout: the stripped files are upstream v5.6 line for line, the resulting fit_event writes an out byte-identical to both builds above, and afterwards --check reports the fork restored with a clean submodule.
  • tests/test_cpu_resume passes on 12cb505 with both builds.
  • The shipped binary gives the same result in two runs; its last-digit differences from the local builds are the toolchain (§2.2).
  • Timings are from one M1 that was also running a BOINC CPU task; three repeats of a variant differed by up to 10 % (most under 5 %), and instruction counts agree with the ratios.
  • Not measured: Linux and Windows builds, mimalloc, any GPU backend. The GPU statement rests on the thread_local + jemalloc row.
  • The benchmark harnesses (a per-seed driver, the threshold-aware Nelder-Mead, the pool allocator) are outside the repository; the regression inputs and fit_event are all that is needed to reproduce the whole-WU numbers.
